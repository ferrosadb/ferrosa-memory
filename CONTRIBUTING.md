# Contributing to Ferrosa Memory

Thanks for your interest. Ferrosa Memory is the structured memory backend for
LLM agents, exposed over the Model Context Protocol (MCP). It builds on
[Ferrosa](https://github.com/ferrosadb/ferrosa) for storage and query.

We welcome contributions of all sizes — bug reports, documentation,
performance improvements, new tools, and additional MCP transports.

## Code of Conduct

This project follows the [Contributor Covenant 2.1](CODE_OF_CONDUCT.md).
Participation is conditioned on adherence to its terms.

## Getting Started

### Prerequisites

- Rust stable (current: see `rust-toolchain.toml` if present)
- A POSIX-ish environment (Linux, macOS)
- Optional: a running Ferrosa instance for integration tests
  (`curl -fsSL https://ferrosadb.com/install.sh | bash` to get one locally)

### Building

```bash
git clone https://github.com/ferrosadb/ferrosa-memory.git
cd ferrosa-memory
cargo build --workspace
```

### Running the Test Suite

```bash
cargo test --workspace        # All crates
cargo test -p ferrosa-memory-core
```

Some integration tests need a live Ferrosa instance and are gated behind
environment variables (e.g. `FERROSA_MEMORY_TEST_FERROSA_ADDR`). They fail loud
with setup instructions when the env is missing — the codebase does not silently
skip tests.

### Hygiene Checklist (Before Every Commit)

1. `cargo fmt` — format
2. `cargo clippy --all-targets -- -D warnings` — lint, zero warnings
3. `cargo test -p <touched-crate>` — affected tests pass
4. `cargo build --all-targets` — full workspace compiles clean

CI runs all of the above on every pull request.

## Development Workflow

### Branching

- Fork the repository and create a topic branch off `main`
- Branch naming: `feat/short-description`, `fix/issue-summary`, `docs/what-changed`
- Never commit directly to `main`

### Commit Messages

Conventional-commit style:

- `feat(crate): summary` — new feature
- `fix(crate): summary` — bug fix
- `refactor(crate): summary` — restructure without behavior change
- `test(crate): summary` — test-only change
- `docs: summary` — documentation
- `chore: summary` — tooling, deps, build

Body explains *why*. The diff already shows the *what*.

### Test-Driven Development

For new tools and bug fixes, write the failing test first, then make it pass,
then refactor. For bug fixes specifically: include a regression test.

### Pull Requests

- Keep PRs focused. One bug fix or one feature per PR.
- Include test coverage. PRs without tests for new behavior will be requested
  to add them.
- Link the issue number if one exists: "Closes #123".
- Mark drafts as drafts. Mark ready-for-review when CI is green.

PRs are squash-merged by default.

## Areas Where Help Is Welcome

- **MCP transport coverage** — additional client compatibility (Claude Desktop,
  Claude Code, third-party agents)
- **Memory-tool ergonomics** — better error messages, smarter argument parsing
- **Performance** — profiling, batch tooling, indexing improvements
- **Documentation** — examples, integration guides, agent-trajectory case studies
- **Test coverage** — property tests, fuzz inputs, agent-trajectory replay

## What We Don't Accept

- Code generated by AI tools without human review and understanding. Using AI
  as an assistant is fine; the contributor must understand and stand behind
  every line they submit.
- Drive-by formatting changes that touch unrelated files.
- Dependency bumps without a stated reason.
- Changes that disable or skip existing tests without replacing them.

## Reporting Bugs

Open a GitHub issue with:

- Ferrosa Memory version (commit hash or release tag)
- MCP client and transport (e.g. Claude Desktop / stdio)
- Reproduction steps, ideally a minimal self-contained example
- Expected vs actual behavior
- Relevant logs (sanitize secrets first)
- Environment: OS, Rust version, Ferrosa version

Security issues — please do **not** open a public issue. See [SECURITY.md](SECURITY.md).
