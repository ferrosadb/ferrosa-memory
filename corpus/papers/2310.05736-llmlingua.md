# LLMLingua: Compressing Prompts for Accelerated LLM Inference

**Authors:** Huiqiang Jiang, Qianhui Wu, Chin-Yew Lin, Yuqing Yang, Lili Qiu
**arXiv:** [2310.05736](https://arxiv.org/abs/2310.05736)
**Published:** October 2023 (updated December 2023)

---

## Summary

As chain-of-thought prompting and in-context learning push prompt lengths into the tens of thousands of tokens, inference cost and latency become prohibitive. LLMLingua introduces a coarse-to-fine compression pipeline: a budget controller first identifies which components (instructions, demonstrations, context) can tolerate the most compression, then a token-level iterative algorithm removes redundant tokens while modeling their interdependence, and finally instruction tuning aligns the compressed distribution with the target LLM. Up to 20× compression with little performance loss.

---

## Key Findings

- **Up to 20× compression** with minimal performance degradation on GSM8K (math reasoning), BBH (multi-step reasoning), ShareGPT (conversation), and Arxiv-March23 (document QA).
- **Coarse-to-fine approach is critical:** Compressing all parts of the prompt equally degrades quality significantly. The budget controller allocates compression ratios based on component importance.
- **Token interdependence modeling:** Naive per-token deletion ignores that removing one token changes the meaning of adjacent tokens. Iterative compression accounts for this.
- **Distribution alignment:** Compressed prompts fed to a different LLM than the one used for compression can degrade quality. Fine-tuning the compressor for distribution alignment is needed for cross-model use.
- **4.5× inference latency reduction** beyond just the token count reduction, due to KV-cache size reduction.

---

## Key Limitations

- Compression is lossy — some information is always discarded.
- Distribution alignment fine-tuning is model-specific; not fully model-agnostic.
- Compression introduces latency that must be paid upfront.

---

## Ferrosa Memory MCP Relevance

LLMLingua is the primary compression algorithm candidate for the storage lifecycle pipeline:

- **Warm-to-cold tier compression:** When a `trajectory_folds` row transitions from NVMe to S3 Standard, the `raw_trajectory` column is compressed via a LLMLingua-style pipeline before write. The 20× compression ratio is the key cost driver — a 10MB raw trajectory becomes ~500KB in cold storage.
- **WASM UDF deployment concern:** LLMLingua requires LLM inference for the budget controller and iterative compression steps. Since Ferrosa WASM UDFs cannot make network calls, LLMLingua must run as an **external sidecar process** (a small Rust/Python service) that the MCP server calls on fold completion, not as a UDF. This is the primary reason the spec lists WASM I/O limits as an open question.
- **Coarse-to-fine budget allocation → memory type awareness:** The budget controller's insight (not all parts compress equally) maps to column-level compression policies: `fold_summary` (high importance, low compression), `raw_trajectory` (medium importance, high compression), `context_snippet` (variable).
- **Alternative: NL-Compress for model-agnostic use:** LLMLingua's distribution alignment requirement makes it less suitable for a multi-model environment. NL-Compress (capsule prompts in natural language) is the fallback for cases where the target model is unknown at compression time.
