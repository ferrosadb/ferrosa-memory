# Prompt Cache: Modular Attention Reuse for Low-Latency Inference

**Authors:** In Gim, Guojun Chen, Seung-seob Lee, Nikhil Sarda, Anurag Khandelwal, Lin Zhong
**arXiv:** [2311.04934](https://arxiv.org/abs/2311.04934)
**Published:** November 2023 (updated April 2024)

---

## Summary

Many LLM prompts share overlapping text segments — system messages, prompt templates, document context. Prompt Cache precomputes and stores the attention states (KV-cache) of frequently repeated segments on the inference server. When a matching segment appears in a new prompt, the cached attention states are reused directly, skipping recomputation. A schema explicitly defines reusable "prompt modules" and ensures positional accuracy on reuse.

---

## Key Findings

- **8–60× latency reduction** for long prompts on document QA and recommendation tasks. The 60× figure is for CPU-based inference; GPU-based inference sees 8× improvement.
- **Positional accuracy is critical:** KV-cache entries are position-dependent. The schema ensures cached segments are inserted at the same position in every prompt that uses them, maintaining correctness.
- **Output accuracy unchanged:** No performance degradation observed — the cached attention states are mathematically equivalent to freshly computed ones when positional constraints are satisfied.
- **Modular prompt design enabled:** Prompt Cache incentivizes decomposing prompts into reusable modules (system prompt, tool descriptions, common context) that can each be independently cached.
- **Segment-level granularity:** Caching at the segment level (not token level) makes the lookup tractable — a segment hash identifies the cached blob.

---

## Key Limitations

- Requires the inference server to maintain the KV-cache store — not directly applicable to API-based LLMs that don't expose KV-cache.
- Cache invalidation when the model version changes requires cache key versioning.
- Memory footprint of cached KV-blobs can be substantial for large models.

---

## Ferrosa Memory MCP Relevance

Every RLM sub-call begins with the same system prompt and the same REPL environment preamble — this is exactly the repeated prefix that Prompt Cache targets:

- **`memo_cache` dual use:** Beyond caching sub-call *results*, the `memo_cache` table can store KV-cache blobs keyed on `(segment_hash, model_version)`. At RLM scale — hundreds of sub-calls per session — the 8× latency reduction compounds dramatically on the shared prefix segments.
- **Model version key:** The `model_version` column in `memo_cache` handles the cache invalidation problem: a model upgrade is a new partition key, and old cached blobs are evicted via TTL.
- **Local inference advantage:** For deployments using local Ollama models (RTX 3090 server), Prompt Cache is directly applicable — the inference server can be instrumented to read KV-blobs from Ferrosa rather than recomputing. API-based deployments (OpenAI, Anthropic) cannot use this without provider support.
- **Tool description caching:** The MCP server's tool schema descriptions are sent to the LLM on every connection. These are a prime candidate for segment-level caching — they never change between sub-calls in a session.
- **Integration path:** Export KV-cache blobs from Ollama's cache to Ferrosa on first computation; subsequent sub-calls within the session skip the prefill step. Latency savings are most pronounced on long system prompts — RLM system prompts are 2–4K tokens based on the paper's appendix.
