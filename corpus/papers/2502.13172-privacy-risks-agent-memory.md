# Unveiling Privacy Risks in LLM Agent Memory

**Authors:** Bo Wang, Weiyi He, Shenglai Zeng, Zhen Xiang, Yue Xing, Jiliang Tang, Pengfei He
**Venue:** ACL 2025 (Main Conference)
**arXiv:** [2502.13172](https://arxiv.org/abs/2502.13172)
**Published:** February 2025

---

## Summary

LLM agents store private user-agent interactions in memory for use as demonstrations in future sessions. This creates a new class of privacy risk: an attacker who can interact with the same agent may be able to extract private information that previous users stored in memory. The paper introduces MEXTRA (Memory EXTRaction Attack), a systematic black-box attack that uses carefully designed prompts to elicit private memory contents from an agent. Both manual and automated prompt generation methods are evaluated. The attack succeeds even without knowledge of the memory system's internals.

---

## Key Findings

- **Memory extraction is feasible under black-box conditions.** The attacker needs only conversational access to the agent — no knowledge of the memory system architecture, database schema, or stored content.
- **MEXTRA framework:** Two attack modes — (1) manual attacking prompt design based on social engineering and prompt injection principles; (2) automated prompt generation using varying levels of knowledge about the agent's role and task domain.
- **Agent designer factors that increase risk:** Verbose memory retrieval (returning full stored entries rather than summaries), weak memory access controls, broad retrieval triggers, and lack of output sanitization.
- **Attacker knowledge amplifies attacks:** Knowing the agent's task domain (e.g., medical records vs. legal documents) significantly improves automated prompt generation quality. Even partial domain knowledge is sufficient.
- **Effective across two representative agent architectures.** Results are not architecture-specific — the vulnerability is in the memory pattern, not the implementation.

---

## Key Limitations

- Focuses on cross-user extraction (attacker extracts data from other users' sessions). Insider attacks and supply-chain attacks are out of scope.
- Defense mechanisms are not proposed; the paper is primarily a threat characterization.

## Ferrosa Memory MCP Relevance

MEXTRA defines the privacy threat model that shapes several design decisions in the spec:

- **Tenant isolation as the primary defense** (spec §7.1): All tables partition on `(tenant_id, ...)` as the first partition key component, and `tenant_id` is extracted from the authenticated session — never from client-supplied input. This makes cross-tenant extraction impossible at the CQL layer regardless of the attacker's prompt sophistication.
- **Retrieval returns summaries, not raw content by default** (spec tool definitions): `retrieve_fold_context` returns fold summaries by default; `include_raw = true` is an explicit opt-in. This directly addresses the "verbose memory retrieval" risk factor identified by MEXTRA. An attacker who can call retrieval tools gets summaries, not verbatim stored content.
- **`raw_trajectory` tiered to cold storage quickly** (spec §7.4): The highest-risk column (verbatim user content) is compressed and tiered to Glacier within 24 hours of folding. Reducing its dwell time in hot storage reduces the window of extraction risk.
- **`DELETE WHERE session_id = ?` cascade** (spec §7.4): Right-to-deletion support ensures that users can purge their stored sessions, removing extractable content entirely.
- **Output sanitization gap acknowledged:** The spec does not currently implement output sanitization on retrieval tool responses — this is a v2 item informed by MEXTRA's finding that output sanitization is a meaningful defense layer.
- **MCP tool access scoping:** `record_outcome` is write-only via MCP; the feedback store is not readable through the MCP interface. This limits what an attacker who has compromised the MCP session can extract.
