# Fractured Chain-of-Thought Reasoning

**Authors:** Baohao Liao, Hanze Dong, Yuhui Xu, Doyen Sahoo, Christof Monz, Junnan Li, Caiming Xiong
**arXiv:** [2505.12992](https://arxiv.org/abs/2505.12992)
**Published:** May 2025 (updated June 2025)

---

## Summary

Long Chain-of-Thought reasoning is accurate but expensive — full CoT generates many tokens before answering, wasting compute on reasoning steps the model doesn't need. The paper first demonstrates that truncated CoT (stopping reasoning early and generating the answer directly) often matches full CoT quality while using dramatically fewer tokens. Building on this, Fractured Sampling interpolates between full CoT and direct answering across three orthogonal axes: number of reasoning trajectories, solutions per trajectory, and truncation depth. Optimal allocation across axes depends on the task and compute budget.

---

## Key Findings

- **Truncated CoT ≈ full CoT** on many tasks, implying most reasoning tokens are redundant.
- **Three-axis framework:** (1) Number of trajectories N (sampling budget), (2) Solutions per trajectory K (answer diversity), (3) Truncation depth D (reasoning depth). These are orthogonal — varying one independently of the others is valid.
- **Log-linear accuracy-cost scaling:** Pass@k accuracy improves log-linearly with token budget when Fractured Sampling is used to allocate compute across axes. Beats pure scaling of any single axis.
- **Steep gains in Pass@k:** The method particularly improves Pass@k (probability any of k samples is correct) — highly relevant for agent scenarios where multiple candidate answers are evaluated.
- **Task-dependent optimal allocation:** Simple tasks should allocate to N (more trajectories, less depth); complex tasks should allocate to D (deeper reasoning, fewer trajectories).

---

## Key Limitations

- Optimal axis allocation is task-dependent and must be tuned per workload.
- Truncation depth selection requires knowing in advance how much reasoning is needed.

---

## Ferrosa Memory MCP Relevance

The three axes of Fractured Sampling map directly to tunable parameters in the MCP server's retrieval layer:

- **Axis 1 (trajectories N) → `limit` parameter on retrieval tools.** How many candidate memory results to retrieve in parallel. The `retrieve_fold_context` and `retrieve_entities` tools expose this as `k`. Default should scale with observed task complexity from `feedback_outcomes`.
- **Axis 2 (solutions per trajectory K) → result diversity in ANN search.** IVFFlat with multiple probe clusters returns more diverse results than HNSW single-probe, at higher latency. For complex tasks, diversity is worth the cost; for simple tasks, a single HNSW probe suffices.
- **Axis 3 (truncation depth D) → `include_raw` flag on `retrieve_fold_context`.** Whether to retrieve the full raw trajectory or just the fold summary. For high-complexity tasks, raw content (full D) is worth the token cost; for simple tasks, the summary suffices (truncated D).
- **Log-linear scaling → cost-accuracy tradeoff documentation.** The MCP server's tool descriptions should document that increasing `k` or enabling `include_raw` has log-linear cost impact, helping the LLM make informed tradeoff decisions.
- **`task_complexity` field in `feedback_outcomes`** tracks which complexity bucket each query belongs to, enabling nightly regression of optimal (N, K, D) defaults per tenant workload profile.
