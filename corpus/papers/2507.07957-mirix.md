# MIRIX: Multi-Agent Memory System for LLM-Based Agents

**Authors:** Yu Wang, Xi Chen
**arXiv:** [2507.07957](https://arxiv.org/abs/2507.07957)
**Published:** July 2025

---

## Summary

Existing agent memory systems use flat, narrow memory components that cannot personalize, abstract, or reliably recall user-specific information over time. MIRIX introduces a modular, multi-agent memory system with six distinct memory types, coordinated by a multi-agent framework that dynamically controls updates and retrieval. The system handles both textual and multimodal (screenshot) inputs, and achieves state-of-the-art results on both LOCOMO (conversation) and ScreenshotVQA (multimodal) benchmarks — the latter representing a 35% accuracy gain over RAG with 99.9% storage reduction.

---

## Key Findings

- **Six memory types, each essential:**
  1. **Core Memory** — essential persistent facts about the user/environment (small, always-present)
  2. **Episodic Memory** — specific past events with temporal context
  3. **Semantic Memory** — generalized knowledge extracted from episodes
  4. **Procedural Memory** — learned skills, workflows, and procedures
  5. **Resource Memory** — pointers to external resources (files, URLs, tools)
  6. **Knowledge Vault** — structured factual knowledge base
- **Multi-agent coordination required:** A memory controller agent dynamically decides what to store in which memory type, what to evict, and how to retrieve across types for a given query.
- **99.9% storage reduction** on ScreenshotVQA vs. storing raw screenshots, while achieving 35% higher accuracy. Selective retention and semantic compression are why.
- **85.4% on LOCOMO** (long-form conversation QA), state-of-the-art.
- **Multimodal memory is newly tractable:** Screenshots can be processed into structured memory entries, making the system applicable to desktop automation tasks (directly relevant to Cowork scenarios).

---

## Key Limitations

- Multi-agent coordination overhead is nontrivial; latency not fully characterized.
- Memory type boundaries are sometimes ambiguous; the controller agent must make judgment calls.

## Ferrosa Memory MCP Relevance

MIRIX's six-type taxonomy is the richest framework for evaluating coverage gaps in the `agent_memory` keyspace:

| MIRIX Type | Ferrosa Coverage | Gap? |
|---|---|---|
| Core Memory | `plan_state` (session goals) | Partial — no global user profile |
| Episodic Memory | `trajectory_folds` (sub-trajectory history) | ✅ |
| Semantic Memory | `entity_store` + `temporal_events` | ✅ |
| Procedural Memory | Not implemented | **Gap — v2 item** |
| Resource Memory | Not implemented | **Gap — v2 item** |
| Knowledge Vault | `entity_store` (structured facts) | Partial |

The multi-agent controller pattern maps to the MCP server's tool routing layer — the router is the memory controller, deciding which index and which table to query for each incoming request. The 99.9% storage reduction result validates the aggressive compression strategy: storing summaries + embeddings rather than raw content is not just cheaper, it's *more accurate*.
