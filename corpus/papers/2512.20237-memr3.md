# MemR³: Memory Retrieval via Reflective Reasoning for LLM Agents

**Authors:** Xingbo Du, Loka Li, Duzhen Zhang, Le Song
**arXiv:** [2512.20237](https://arxiv.org/abs/2512.20237)
**Published:** December 2025

---

## Summary

Most deployed memory systems optimize compression and storage but treat retrieval as a simple retrieve-then-answer pipeline with no closed-loop control. MemR³ reframes memory retrieval as an autonomous agent decision: at each step the system chooses between *retrieve* (fetch more evidence), *reflect* (synthesize what it has), or *answer* (respond with confidence). An evidence-gap tracker maintains an explicit representation of what is known and what is still missing, making the retrieval process transparent and auditable.

---

## Key Findings

- **Closed-loop > open-loop retrieval:** The route/reflect/answer loop consistently outperforms single-shot retrieve-then-answer on complex multi-hop memory queries.
- **+7.29% over vanilla RAG** and **+1.94% over Zep** on LoCoMo benchmark using GPT-4.1-mini — and MemR³ is designed as a plug-in controller over existing stores, not a replacement.
- **Evidence-gap tracker:** Explicitly tracks which aspects of the query remain unanswered. This transparency makes the system debuggable — you can inspect exactly what evidence was collected and what was missing.
- **Plug-and-play:** MemR³ wraps any memory store (RAG, Zep, custom) without modifying the underlying storage. The controller is separate from the store.
- **Three-action vocabulary** (retrieve, reflect, answer) is minimal and sufficient — additional actions did not improve results in ablations.

---

## Key Limitations

- Multiple retrieval rounds increase latency; not suitable for strict latency budgets.
- Evidence-gap tracker quality depends on the controller LLM's ability to articulate what it doesn't know.

---

## Ferrosa Memory MCP Relevance

MemR³'s architecture maps cleanly onto how Claude Code should interact with the MCP server:

- **The three-action vocabulary as MCP tool usage pattern.** The LLM's interaction with ferrosa-memory-mcp should follow the same pattern: call `retrieve_fold_context` or `retrieve_entities` (retrieve), process results (reflect), then either answer or retrieve again. The MCP server's tool descriptions should make this loop explicit.
- **Evidence-gap tracker as a memory query state.** The `plan_state` table can hold an evidence-gap structure alongside the goal text — what evidence has been collected, what is still outstanding. This makes the retrieval loop resumable and auditable.
- **Plug-and-play validation.** MemR³'s ability to wrap any store confirms that the MCP server's thin-adapter architecture is correct: the intelligence (routing, reflection) stays in the LLM; the server just provides fast, typed access to Ferrosa.
- **+7.29% over RAG confirms the memory investment.** Even a well-built static RAG system is measurably inferior to a memory system with temporal chaining and closed-loop retrieval. This quantifies the business case for building the full Ferrosa memory stack rather than a simpler embedding lookup.
