# MCPShield: A Security Cognition Layer for Adaptive Trust Calibration in MCP Agents

**Authors:** Zhenhong Zhou, Yuanhe Zhang, Hongwei Cai, Moayad Aloqaily, Ouns Bouachir, Linsey Pang, Prakhar Mehrotra, Kun Wang, Qingsong Wen
**arXiv:** [2602.14281](https://arxiv.org/abs/2602.14281)
**Published:** February 2026

---

## Summary

The Model Context Protocol standardizes tool use for LLM agents and enables third-party servers to expose tools. This openness creates a security misalignment: agents implicitly trust tools exposed by any MCP server, including potentially malicious ones. MCPShield is a plug-in security cognition layer that monitors the full tool invocation lifecycle — probing server metadata before invocation, constraining execution within controlled boundaries, and updating security cognition by reasoning over post-invocation traces. Tested against six novel MCP attack scenarios across six LLMs; strong generalization with no false positives on benign servers.

---

## Key Findings

- **LLMs implicitly trust MCP tools.** Without intervention, agents will invoke any tool a server exposes without validating the server's identity or the tool's claimed behavior.
- **Three-phase security cognition:** (1) Pre-invocation: metadata-guided probing to form a prior about the server's trustworthiness; (2) Execution: constrain within controlled boundaries; (3) Post-invocation: reason over traces and update security cognition.
- **Six attack scenarios defended:** Tool poisoning, parameter injection, response manipulation, identity spoofing, capability inflation, and data exfiltration — all mitigated with high generalization.
- **No false positives on benign servers** across tested models — security hardening does not degrade normal tool use.
- **Low deployment overhead** — MCPShield adds minimal latency and can run as a transparent proxy layer.
- **Human experience analogy:** The design is explicitly inspired by how humans validate tools: check reputation before use, stay alert during use, reflect on experience after use.

---

## Key Limitations

- Pre-invocation probing requires some form of server metadata (name, description, claimed capabilities) — servers with no metadata cannot be probed.
- Post-invocation reasoning adds latency per tool call.

---

## Ferrosa Memory MCP Relevance

MCPShield informs the security design of ferrosa-memory-mcp from both sides — as a server being defended against attack, and as a server that should behave in ways that pass MCPShield's validation:

- **Tool schema design should satisfy MCPShield's metadata requirements.** The server manifest must include accurate, specific descriptions of each tool's behavior, expected inputs, and what it accesses. Vague descriptions trigger MCPShield's distrust signal.
- **Explicit access declarations.** The MCP server should declare what data categories each tool touches (e.g., `retrieve_entities` reads from `entity_store`, writes to `feedback_outcomes`). This makes MCPShield's pre-invocation probing deterministic.
- **Execution boundary constraints.** The spec's `enum` type constraints on `strategy`, `entity_type`, and `status` fields are MCPShield-compatible: they bound the parameter space to known-safe values, preventing parameter injection attacks.
- **Post-invocation audit trail.** The append-only audit log in the spec is the data source MCPShield-style reasoning needs to validate that the tool behaved as claimed.
- **`record_outcome` as cognition update.** The feedback loop implemented by `record_outcome` is structurally identical to MCPShield's post-invocation cognition update — the server itself is reasoning over its own behavior history to improve routing decisions.
