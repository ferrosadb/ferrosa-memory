# Think, But Don't Overthink: Reproducing Recursive Language Models

**Authors:** Daren Wang
**arXiv:** [2603.02615](https://arxiv.org/abs/2603.02615)
**Published:** March 2026

---

## Summary

An independent reproduction study of the RLM paper using DeepSeek v3.2 and Kimi K2, specifically investigating what happens when recursion depth is increased beyond 1. The core finding: depth=1 RLMs reliably improve complex reasoning tasks, but depth=2 causes "overthinking" — exponential blowup in execution time and cost, often with degraded accuracy. The model re-derives answers the parent already held, enters verification loops, and fails to return stored results from the code environment.

---

## Key Findings

- **Depth=1 confirmed:** Replicates the original paper's core result on S-NIAH and OOLONG benchmarks with open-source models.
- **Depth=2 is dangerous:** Execution time blows up from 3.6s to 344.5s on some tasks. Cost increases exponentially, not linearly.
- **Overthinking pattern:** At depth=2, models enter redundant verification loops, re-derive results already stored in REPL variables, and sometimes fail to return the stored answer (returning a freshly generated wrong answer instead).
- **Simple retrieval tasks regress:** On S-NIAH (simple retrieval), even depth=1 RLMs underperform the base model. RLMs are net-negative for problems the base model can handle natively.
- **Open model behavior differs:** Kimi K2 and DeepSeek v3.2 exhibit more aggressive sub-calling behavior than GPT-5, requiring explicit batching instructions in the system prompt to prevent per-line sub-calls.

---

## Key Limitations

- Single author, smaller scale than original paper.
- Only tests depth 0/1/2; doesn't explore fractional or adaptive depth.

---

## Ferrosa Memory MCP Relevance

- **Primary motivation for the memoization layer.** The "overthinking" pattern is exactly what the `memo_cache` table prevents: when the parent LLM would re-derive an already-computed result, it hits the cache instead. The content-hash key ensures identical sub-queries get the stored result.
- **Hard cap at depth=1 is a design constraint.** The MCP server should not expose any tool that encourages recursive memory lookups. All retrieval tools are leaves — they query Ferrosa and return, never triggering further recursive calls.
- **Simple task bypass.** The finding that RLMs hurt on simple tasks means the `check_memo_cache` tool should return a `skip_memory` hint when the query embedding is highly similar to queries that succeeded without memory in `feedback_outcomes`.
- **Thundering herd connection.** The depth=2 blowup is structurally similar to a cache stampede: multiple sub-calls converge on the same result. The idempotency key pattern on `store_memo_result` directly addresses this.
