# ADR-006: Session Task Continuity

## Status

Accepted.

## Context

Long-running agent sessions can lose their place after compaction or restart
when the only recall source is noisy semantic memory. The system already owns
durable session state, hooks, MCP tools, temporal turn links, search, recall,
and schema migrations. Active task state belongs in this same layer so every
client benefits, including Hermes, gateway threads, cron jobs, Claude/Codex via
MCP, and future agents.

The existing `plan_*` tools support hierarchical decomposition, but they are not
the complete user-facing work-item model. A visible task system needs lifecycle
operations, scoped aliases, focus management, multiple active tasks, recovery
hints, compaction injection, and deterministic behavior when semantic context is
irrelevant.

## Decision

Add a client-visible `session_task` model owned by `ferrosa-memory`.

The canonical task ID is generated by fmem. Agents and clients may provide
idempotency keys or scoped aliases, but they must not invent authoritative task
identifiers.

Multiple tasks can be active in one session. fmem maintains a deterministic
foreground task and a persisted focus stack. When user work shifts, fmem can
push the prior foreground task down the stack and focus the new task. When the
foreground task closes, fmem can pop the previous task and either ask whether to
resume or inject an auto-resume prompt, depending on session policy.

The `session_task` model is the client-visible work-item surface while tasks are
in flight. Planning behavior remains available when there are no current tasks
or when the user explicitly asks to plan more work. This reduces drift while
allowing long sessions to evolve as new facts and requirements appear.

Task deletion is not a normal lifecycle operation. Client deletion maps to
`cancelled` or `superseded`; destructive erasure remains limited to explicit
privacy/session cleanup paths.

The v1 task-shift classifier is deterministic. A v2 LLM judge may be added as
an optional policy-controlled enhancement, but no deployment should require a
large model to preserve task continuity.

## Consequences

- fmem becomes the source of truth for active task continuity.
- Clients such as Hermes can treat local todo stores as caches.
- Compaction and session-start hooks can inject compact structured task state
  instead of relying on semantic search.
- Task state needs versioned, query-shaped app-owned CQL tables registered
  through the migration pipeline before implementation.
- Existing `plan_*` tools should either become compatibility wrappers or remain
  a lower-level planning surface that does not compete with `session_task`.

## Required Controls

- All schema changes must use an ordered, data-preserving migration.
- Task tables are app-owned fmem tables; graph-owned backing tables are not
  involved.
- Recovery hints must be structured so clients can act deterministically.
- Recall injection must be token bounded and avoid completed/cancelled history
  unless explicitly requested.
- Scoped aliases must fail loud on ambiguity instead of guessing.
